## Section 0 — 回顾：我们已经解决了什么，下一阶段还缺什么

### 0.1 本次分享希望形成什么共识

- 对齐下一阶段重点验证的产品方向
- 从产品流程中识别可复用的基础设施需求
- 讨论架构选项，但不预先将某个选项作为结论
- 最终确定首批验证任务、责任边界和决策条件

### 0.2 当前三条工作线及其不同职责

- **Mantle v2 的 Glamsterdam 适配**
  - 这是必须完成的基础工作，不依赖新产品是否成功
  - 保障 L1 升级后的派生、批次提交和跨链消息正常运行，同时保留现有 L2 EVM 规则
- **mStocks 产品的开发**
  - 按当前产品设计，通过直连券商的方式引入美股相关资产到链上
  - 回答“用户可以在 Mantle 上持有和交易什么”
- **PropAMM、聚合器和链下做市实验：补充交易执行能力**
  - 回答“用户能否以合理价格成交”
  - 后续应作为产品之间的公共能力，成为所有产品中获取资产的最佳方式

### 0.3 为什么我们做这些事情：从资产供给与 TVL 积累，走向高质量交易

- **为什么做 mStocks：抓住“美股周期 + 资产上链”的机会**
  - 我们当前的市场判断是，“美股周期 + 资产上链”是值得投入的方向。
  - mStocks 是我们承接这一机会的产品：
    - 通过直连券商的方式，将美股相关资产引入 Mantle。
    - 为 Mantle 增加一类有明确链外市场基础的资产，而不只是增加链上原生资产。
  - 因此，mStocks 首先解决的是**资产供给问题：Mantle 上有什么值得用户持有和交易的资产。**
- **为什么不止于引入资产：Mantle 的优势在于 TVL 积累，但 TVL 不是充分的目标**
  - Mantle 已经积累了一定的 TVL，这是我们的基础优势。
  - 但我们不希望只围绕“有多少资金留在链上”来评价生态：
    - TVL 反映资产沉淀规模，不直接反映这些资产是否被有效使用。
    - 资产进入池子，不代表当前价格附近就有足够的有效交易深度。
    - 有资金、有资产，也不代表有持续的交易需求和良好的成交体验。
  - **我们下一阶段更关注的是：这些资产是否产生了真实、持续的交易，以及用户能否以合理的价格成交。**
  - 因此，我们的方向不是否定 TVL，而是希望将资产沉淀优势进一步转化为交易优势。

**一个具体例子：Fluxion 上的 xStocks 池子**

![Fluxion Lp](/images/fluxion-lp.png "Fluxion Lp")

- 根据我们此前对相关池子的调研，流动性是平铺的，而不是集中在当前交易价格附近。
  - 池子里虽然有资金，但这些资金并没有高效地转化为当前价格附近的可执行深度。
  - 从已有报价测试来看，用户实际得到的报价并不好。
  - 这体现了一个问题：**看起来有流动性，不等于用户交易时能获得好价格。**

- 分享时可以在这里展示两类证据：

- 这个例子要支持的结论不是“TVL 是假的”，而是：
  - **仅看 TVL，会高估资产的实际可交易性；我们需要同时关注有效深度、资金利用效率和成交质量。**

- **为什么做 PropAMM：补齐从“有资产、有资金”到“能高质量交易”的环节**
  - mStocks 解决资产供给，但不会自动解决这些资产进入链上之后的报价问题。
  - 因此，我们希望通过 PropAMM，以及配套的聚合器和链下做市能力，探索更好的报价与执行方式：
    - 根据市场价格和自身库存，更灵活地调整报价。
    - 提高用于报价的资金利用效率。
    - 通过聚合与路由，为用户寻找更好的可执行价格。
  - 这项工作的目标不是再增加一个沉淀 TVL 的池子，而是**提高用户实际交易时的成交质量**。
  - 对应的评价指标也应从单纯的资金规模，扩展到：
    - 相同订单规模下的报价偏离、滑点和可成交深度。
    - 报价与执行的稳定性。
    - 在此基础上，真实交易用户是否增加、是否持续回来交易。
- **小结：当前几项工作共同指向什么**
  - **mStocks：引入值得持有和交易的资产。**
  - **Mantle 的 TVL 积累：提供已有的资产与资金基础。**
  - **PropAMM：探索如何让这些资产获得更好的报价和交易体验。**
  - 我们希望从“链上有多少资产”，进一步走向“这些资产被怎样使用，以及产生了多少高质量交易”。

### 0.4 衔接：有了资产和更好的报价，为什么用户还会持续交易？

- 资产供给和交易质量，是我们正在补齐的两个环节。
- 但**更好的报价解决的是“交易时体验如何”，还没有完全回答“用户为什么要来交易、为什么会持续交易”。**
- 所以下一步，需要探索新的资产发行和交易场景：
  - Agentic Meme Launchpad：验证新的资产发行、分发与参与方式。
  - Perps：验证更多交易、风险表达与对冲场景。
- 再从这些产品的具体流程中，抽象出我们需要建设的 chain infra 能力。

### 0.4 下一阶段的核心叙事

- 从“引入更多资产”，走向“让资产进入可持续运转的交易市场”。
- 围绕两个产品方向验证：
  - **Agentic Meme Launchpad：** 验证新的发行、分发与参与方式。
  - **Perps：** 验证持续交易、风险表达和对冲需求。
- mStocks 和 PropAMM 不退出主线：
  - 前者提供资产供给。
  - 后者提供报价、路由和做市能力。
  - 新产品与它们的协同，通过具体资金和订单路径验证。

**本节结论：我们不是为了增加链上交易数量而增加场景，而是要找到能够产生持续需求、并由现有资产和执行能力承接的产品。**

## Section 1 — 产品拆解：两个产品究竟解决什么问题，需要什么能力

### 1.1 Agentic Meme Launchpad

#### 1.1.1 先复盘：为什么不值得再做一个普通 Launchpad

- 将此前两个项目的复盘放在方案介绍之前。
- 用用户漏斗和市场表现区分：
  - 分发不足。
  - 激活、入金或交易转化不足。
  - 资产发行后缺少持续需求。
  - 二级市场执行质量不足。
  - 技术体验成为实际阻碍。
- 明确这次准备改变哪几个条件，哪些条件尚未改变。

#### 1.1.2 新方案的产品假设

- Bybit AI 作为潜在入口，但需要验证入口位置、接入方式和实际转化。
- Agent 作为主要交互与执行主体：
  - 帮助用户发现、创建或参与资产交易。
  - 在用户授权范围内执行操作。
- AA 钱包作为当前方案中的账户基础：
  - 权限边界、预算和有效期。
  - Gas sponsorship。
  - 批量操作、权限撤销和必要的并发支持。
- 不将 Agent 数量直接视为用户规模：
  - 需要识别背后的独立用户、资金来源和真实交易意图。

#### 1.1.3 展示完整 workflow

- 入口与用户激活。
- 钱包创建／接入及授权。
- 资产创建或发现。
- 初始发行与交易。
- 二级市场接入，以及流动性迁移流程——如已有设计包含该环节。
- 后续交易、权限管理和退出。

对每个步骤标注：**用户在做什么、Agent 在做什么、哪些约束必须由合约或协议强制执行。**

#### 1.1.4 明确与 mStocks、PropAMM 的连接

- 展示具体交易路径，而不是只画产品之间的连接箭头。
- mStocks 在该路径中承担什么角色？
- PropAMM 提供什么服务，库存和风险由谁承担？
- 没有验证过的连接，明确标注为产品假设。

#### 1.1.5 抽象出的基础设施需求

- 安全、可撤销的自动化授权。
- 可靠的交易提交、状态查询和失败恢复。
- 可控的代付成本与滥用防护。
- 发行高峰期的交易处理和明确的排序规则。
- 面向 Agent 的 SDK、事件订阅与操作审计。

**本节结论：Launchpad 对基础设施的核心要求，不是“支持某个 AA 提案”，而是让自动化参与安全、顺畅且成本可控。**

### 1.2 Perps

#### 1.2.1 先定义目标产品，而不是先讨论执行架构

- 目标用户是谁：普通交易者、做市商、对冲需求方，还是策略工具？
- 主要交易哪些市场，与现有资产供给有什么关系？
- 为什么用户和做市商会迁移过来？
- 选择什么交易模型：
  - 资金池／预言机模型。
  - 混合撮合与链上结算模型。
  - 可验证的链上订单簿与撮合模型。

#### 1.2.2 展示完整 workflow

- 入金与保证金管理。
- 授权、下单、撤单与改单。
- 订单排序与撮合。
- 仓位、保证金和风险检查。
- 价格输入、资金费率与清算。
- 提现及异常情况下的退出。

逐项说明：**哪些状态是权威状态、谁有权更新、谁验证结果，以及失败时如何恢复。**

#### 1.2.3 将“高性能”拆成可衡量要求

- 下单和撤单的响应时间，以及生效时间。
- 正常负载与突发负载下的 P95／P99 延迟。
- 单一热门市场的处理能力，而不只是多市场总吞吐。
- 每秒订单消息、撤单和风险更新数量，而不只是 TPS。
- 每笔操作、每笔成交的完整成本。
- 明确区分 API 应答、排序器预确认、状态落定与结算最终性。

#### 1.2.4 不止需要一个快速撮合引擎

- 需要明确价格输入、风控、清算和异常处理机制。
- 需要做市商接入、行情分发和稳定的交易接口。
- 需要确定产品运营与风险管理的责任方。
- 把“能跑撮合 benchmark”和“能运营一个 Perps 市场”分开验收。

**本节结论：先确定交易模型、目标体验和安全边界，再判断现有 Mantle 是否不足。**

## Section 2 — 从产品需求到能力差距：哪些事情真的需要改链

这一节是原大纲最值得新增的部分。它承担“产品需求 → 技术方案”的桥接作用。

### 2.1 统一整理需求，但不要提前认定都是协议缺口

| 能力方向 | 产品所需能力 | 首先评估的实现层 |
| :-- | :-- | :-- |
| 安全自动化账户 | 受限授权、撤销、预算、代付、批量操作 | 钱包合约、SDK、Bundler／Paymaster |
| 可靠交易通路 | 提交、订阅、确认、重试、低尾延迟 | RPC、交易服务、排序器与执行流水线 |
| 专用交易逻辑 | 撮合、仓位、保证金、清算、确定性回放 | 应用合约或专用状态机 |
| 资产复用与组合 | 资产转入转出、共享资金使用、跨产品交互 | 账户与资产接口、消息和结算设计 |
| 安全与可运营性 | 状态验证、数据可用性、故障恢复、退出 | 协议、证明／验证系统和运维体系 |

### 2.2 每项能力都要说明五件事

- 当前已有能力与测量基线。
- 目标要求。
- 差距来自哪个环节。
- 最小必要改动是什么。
- 如何验证改动确实解决了问题。

### 2.3 保留两条技术主线，但避免过度简化

- **主线 A：生产可用的自动化账户能力。**
- **主线 B：满足交易要求的执行能力。**
- 排序、数据服务、状态验证、资产交互与运维，是两条主线的共同约束，不能因只总结成“AA + 状态机”而被遗漏。

**本节结论：Roadmap 应围绕已识别的能力差距，而不是围绕想实现的 EIP 或架构名称。**

## Section 3 — AA 路线：先交付可用能力，再决定是否推进 Native AA

### 3.1 明确“已支持”与“产品可用”的差别

- 沿用你给出的 ERC-4337、EIP-7702 已支持这一前提，但补充端到端验收：
  - 钱包实现是否经过验证？
  - Bundler、Paymaster、RPC 和 SDK 是否稳定可用？
  - 权限撤销、失败重试、代付预算是否形成完整流程？
- ERC-4337 是无需修改共识层的账户抽象方案；EIP-7702 提供 EOA 代码委托机制。二者可以配合使用，不应作为完全互斥的方案比较。

### 3.2 第一阶段：围绕实际产品交付 AA 能力

- 优先解决：
  - Session key 或其他受限授权。
  - 合约、方法、资产和金额范围约束。
  - 权限过期、撤销及紧急停止。
  - Gas sponsorship 的预算、限流与防滥用。
  - SDK、监控和参考集成。
- 将 2D nonce 放在具体并发需求下讨论：
  - ERC-4337 已包含 `key + sequence` 的 nonce 机制，不必为了多 nonce 通道先等待 Native AA。
  - 同时区分“允许多个独立请求通道”和“底层状态能够并行执行”。
- 不把 AA 限定为 Launchpad 专属：
  - Perps 的入金、资金管理和授权同样应考虑复用。
  - 高频订单签名与验证路径需要单独设计，不预设每条订单都必须成为一笔 UserOperation。

### 3.3 第二阶段：评估 Native AA 的增量价值

- **RIP-7560：** 将账户验证、执行和付费等机制纳入协议层。
- **EIP-8130：** 当前官方文本为 _Keystore Accounts_，围绕账户授权配置、认证器和新交易类型组织能力。
- **EIP-8141：** 通过 Frame Transaction 组织验证、执行和 Gas 支付。
- 截至 **2026 年 9 月 22 日**，上述官方文本均标记为 Draft；应将“规范状态”“Mantle 实现状态”和“生态部署成熟度”分开讨论。
- 比较重点：
  - 能解决当前方案中的哪个真实问题？
  - 成本和交易纳入路径改善有多大？
  - 引入哪些验证、DoS 防护和工具兼容要求？
  - 客户端、证明／验证系统及长期维护成本如何？

**本节结论：先承诺可用的账户产品与开发者接口，不将尚未选定的 Native AA 方案设为产品上线前置条件。提案细节可移入附录。**

## Section 4 — Perps 执行路线：在统一标准下比较三个选项

### 4.1 先澄清比较维度

- 建议少用“水平扩展／垂直扩展”作为核心分类，改用：
  - **现有 L2 通用执行环境。**
  - **Mantle 统一验证边界内的专用执行模块。**
  - **独立执行域、在 Mantle 结算的 App-specific L3。**
- “是否使用专用状态机”和“在哪一层结算”是两个不同维度：
  - 不能把专用执行的全部优势都归因于 L3。
  - 也不能因为部署了 L3，就默认获得目标性能。

### 4.2 方案 A：继续在 Mantle L2 上实现和优化

- **方案内容**
  - 先实现选定交易模型的最小版本。
  - 定位瓶颈是否在应用逻辑、状态访问、交易提交、排序或区块执行。
  - 根据测量结果进行针对性优化，并评估与外部项目合作。
- **重点验证**
  - 在目标负载下，延迟、成本、正确性是否达标？
  - 单一市场高峰是否影响其他应用？
  - 优化是否会增加整个网络的验证和运行负担？
- **选择条件**
  - 若满足产品要求，应将它作为优先基线，而不是因为缺少新架构而排除。
  - 商业竞争力由用户、流动性和执行质量验证，不由“是否链下撮合”单独决定。

### 4.3 方案 B：引入专用执行模块，与 EVM 环境紧密集成

- **方案内容**
  - 用针对性状态机处理撮合、仓位和风控。
  - 明确该状态机如何进入 Mantle 的状态派生、状态承诺和验证流程。
- **借鉴 Hyperliquid 时应讲清楚**
  - HyperCore 与 HyperEVM 共享 HyperBFT 共识，并非简单将外部撮合服务挂到 EVM 上。
  - 同时，CoreWriter 的订单操作存在入队与延后执行机制，因此不能把这种集成直接等同于任意同步、原子的 DeFi 组合。
- **必须回答的问题**
  - EVM 能同步读取什么状态？
  - 写操作何时生效，失败如何反馈？
  - 哪些跨环境操作能够共同成功或共同回滚？
  - 专用模块的错误会影响哪些其他应用？
  - 如何验证其执行结果，如何升级与恢复？
- **关键边界**
  - 如果引擎实际上是独立服务，只向 Mantle 提交结果，就必须单独说明证明或信任机制，不能直接套用“同一安全域”的叙事。

### 4.4 方案 C：App-specific L3，以 Perps 作为第一个验证场景

- **方案内容**
  - 独立执行域，根据业务选择状态机与排序方式。
  - 在 Mantle 上完成定义明确的验证和结算。
  - 将资产与消息跨域路径作为核心设计，而不是后补接口。
- **可以争取的收益**
  - 针对业务的执行和资源配置。
  - 独立费用机制、账户模型及升级节奏。
  - 应用级执行资源隔离。类似定制执行、费用和资源管理能力也出现在现有 Appchain 框架中，但这些是具体设计能力，不是“L3”名称本身的保证。
- **需要对原大纲中的优势补充限定条件**
  - **“抛弃 EVM／MPT”：** 可以评估专用执行与其他状态结构，但必须说明替代的状态承诺、可验证执行和恢复方案。
  - **“天然拥堵隔离”：** 明确隔离到哪一层；检查是否仍共享排序器硬件、DA、证明资源或父链结算通道。
  - **“手续费进一步下降”：** 比较执行、DA、证明／结算、运维摊销与跨域操作的完整成本。尤其在尚未验证用户量时，不能忽略固定成本。
  - **“可以审查交易”：** 改为讨论明确的业务准入与排序规则，同时说明治理权限、透明性和合法用户退出路径。这是取舍，不是无条件优势。
  - **“资产仍然可组合”：** 分别说明资产可转移、状态可读取、消息可交互和交易可原子组合，不能合并为一个结论。
- **最重要的业务验证**
  - 用户是否需要频繁在 mStocks、现货市场与 Perps 之间移动资金？
  - 跨域时延和资金占用是否抵消执行收益？
  - 统一前端与统一账户之外，是否真正解决了资金使用和资产交互问题？

### 4.5 三个方案如何做选择

- 使用同一业务负载、可比资源和同一验收口径比较：
  - 延迟与吞吐。
  - 正确性与安全假设。
  - 资产复用和交互语义。
  - 完整成本。
  - 开发、验证、运维和升级负担。
- 建议的判断顺序：
  - A 满足要求：优先交付产品。
  - A 不满足，且紧密组合是硬要求：重点验证 B。
  - A 不满足，而独立执行、定制规则和隔离更重要：重点验证 C。
- **先证明一个 Perps 专用执行场景成立，再决定是否建设通用的多 Appchain 平台。**

**本节结论：L3 是有条件成立的候选架构，而不是由“我们要做 Perps”自然推出的唯一答案。**

## Section 5 — Roadmap：哪些现在做，哪些验证后做，哪些暂不承诺

### 5.1 必做基础线：不与产品实验绑定

- 完成兼容性、安全与可靠性工作。
- 建立现网交易路径和执行性能基线。
- 补齐可观测性、故障定位和恢复能力。
- 明确这些工作的交付不等待 Launchpad 或 Perps 验证结果。

### 5.2 第一阶段：补齐可复用能力，验证产品假设

- **AA**
  - 交付参考钱包、权限方案、SDK 和可靠交易服务。
  - 通过 Launchpad 的完整用户流程验收。
- **Launchpad**
  - 验证入口、授权、入金、首笔交易与后续留存。
  - 验证与 mStocks、PropAMM 的连接是否真实成立。
- **Perps**
  - 明确目标交易模型和主要市场。
  - 建立最小实现、正确性测试与负载模型。
  - 在现有 Mantle 条件下测量，而不是先假设无法满足要求。

### 5.3 第二阶段：根据证据决定协议与执行架构投入

- 现有 AA 方案出现明确限制，再决定 Native AA 的投入范围。
- 现有 L2 未满足产品要求，再推进专用模块或 L3 对比验证。
- 验收不仅包括引擎速度，还包括：
  - 状态回放与验证。
  - 极端负载和故障场景。
  - 资产进出与异常退出。
  - 完整运行成本。

### 5.4 第三阶段：产品化与推广

- 先完成首个场景的安全审查、上线演练、监控和应急方案。
- 明确小范围验证到扩大使用的条件。
- 出现第二个实质性需求后，再判断哪些能力值得平台化。
- 避免首个应用尚未验证，就同时承担通用 Appchain 框架、跨域系统和多种状态机的建设成本。

### 5.5 本次讨论必须形成的决策

- **范围：** 什么属于 Mantle v3，什么属于后续探索？
- **责任：** 产品、做市与风险运营、应用开发、chain infra 分别由谁承担？哪些自建，哪些合作？
- **首批任务：** 每项列出负责人、交付物、验收指标、依赖和目标日期。
- **决策门槛：** 哪些结果触发进一步投入，哪些结果意味着暂停或换路线？
- **暂不做清单：** 明确当前不承诺哪些协议提案、通用化能力或架构迁移。
