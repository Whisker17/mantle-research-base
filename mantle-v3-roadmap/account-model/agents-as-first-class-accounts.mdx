## 0. Background 信息 

传统 EOA 可以由人类或程序控制，但其默认账户权限较粗、交易使用单一递增 nonce，且自付交易需要原生币余额。对于长期在线、多任务并发且需要受限授权的 Agent，这些默认特征会增加密钥管理、任务调度和费用管理的复杂度。 当 agents 成为链上最大消费者之后，我们需要重新审视账户模型是否依然适配 agents，角色的变化导致了一些根本性的转变：

1. 执行主体由人转向链下自动化进程：由 agents 或自动化套利/高频做市 Bot 负责持续监控并触发交易
2. 频率由低频交互转向超高频突发响应：如 Meme Launchpad 极速抢买（毫秒级）、Perps 动态对冲与清算保护（高并发、严苛时间窗口）
3. 决策链路解耦：资本所有权（比如金库 DAO）与策略执行权（即云端运行的 Agent 实例）必须物理分离

## 1. 当前 EVM 账户模型存在的问题 

如果我们依然沿用当前的账户模型，则会出现以下几个致命问题：

1. **私钥安全与信任边界**
   1. 这个问题主要就是因为在 EOA 中地址由私钥的公钥哈希派生而来（`keccak256(pubKey)[12:]`），签名验证仅依赖 `ecrecover`，即拥有私钥就拥有该账户的一切资产与完全控制权
   2. 但是对于 agents 来说，其运行的环境是一个易受攻击的场所，包括运行在云端/docker 中，大量的 AI Runtime 风险（比如 Prompt Injection，Jailbreak，Skills 后门等），大量的供应链攻击
   3. 因此将私钥完全交给 agents 是一个非常危险操作，如果我们选择使用 multisig，那就会引入一个潜在的异步延迟，无法满足 Meme 抢跑与合约高频对冲这类场景
2. **串行 Nonce 的设计**
   1. 目前的 evm 设计中设置的执行顺序是严格按 Nonce 递增串行执行，这对于高频 Agents 来说是一个限制，比如当 agent 在 Meme Launchpad 上监听新代币创建并挂单买入（分配 Nonce = 10）的同时在 Perps 市场上为现有空头头寸追加保证金或调整止损单（分配 Nonce = 11），如果任务 A 由于设置的 Gas Price 略低、或者触发了底层合约的临时拥堵而卡在 Mempool 中，即使任务 B 开出了 1000 Gwei 的天价 Gas，也会因为 Nonce = 10 未上链而强制卡死在队列中！ 结果是：Perps 仓位因无法追加保证金被强制清算，产生系统性爆仓
   2. 目前的解决方案有两个：
      1. 加 gas 然后用相同的 nonce 冲掉之前的那笔交易
      2. 开多个 eoa 进行统一管理
3. **Gas Token 的缺乏**
   1. 在 EVM 规范中，交易发起者必须直接消耗账户内的原生代币（以太坊上为 ETH，Mantle 上为 MNT）作为 Gas，而几乎所有的用户在 onboarding 的时候都没有原生 gas token，因此无法完成交易 

当然，除了上面说的这些，还有一些 evm 账户模型的限制，但是对于 Agentic AA 来说并不是第一重要的，比如签名算法的限制，native multicall 功能之类的。

## 2. Mantle 目前的产品方向 

在我们之前的介绍中，我们总结了 Mantle 的叙事核心是**资产发行和资产交易**，而核心的产品应该是 meme Launchpad 和 perps，核心用户应该是 agents，那么我们在这里针对核心产品进行一个针对账户模型的分析。 

### 2.1 Meme Launchpad 的业务场景对账户的需求 

简单总结一下在 meme Launchpad 场景下的业务需求和用户行为：

- 业务需求
  - 将 mStocks 作为 quote token 进行 meme 发射（因此有获取 mStocks 的需求）
  - Meme 毕业后可以自动将流动性迁移到更加优质的 DEX 中
- 用户行为
  - 追求极速打新的 agents，常驻监控链上工厂合约与社交媒体新闻流，在代币部署首个区块内毫秒级抢买
  - 普通散户授权 Agent 根据策略自主跟随知名交易员或情绪指标进行买卖以及组 LP 

因此我们总结了该场景下核心的账户需求：

1. **授权与执行的原子批处理**

- 在传统 EOA 模型中，Agent 要用 NVDAx 参与打新，必须分步执行：
  1. 第一步：发送 `NVDAx.approve(LaunchpadPool, amount)`；
  2. 第二步：等待前序交易落块确认（在 2.0s 块时间的 Mantle 上至少需 2 秒）；
  3. 第三步：发送 `LaunchpadPool.buy(NVDAx, amount, minTokensOut)`。

- 在尚未建立代币支出授权的情况下，Agent 使用 mStocks 参与打新，通常需要先授权，再调用买入接口。即使两笔交易可以连续提交，其成功与失败状态也不天然绑定。
- 账户应支持在一次交易中完成“必要的报价资产兑换 → 设置支出授权 → 买入 → 校验最低获得数量”，并在任何关键步骤失败时回滚整个业务批次，避免留下非预期的授权或中间资产状态。
- 这里的核心需求是账户上下文中的原子执行能力，并不要求一定由 Native AA 提供。

2. **Session Keys**

- 主账户必须能够向打新 Agent 签发具有极窄权限的 Session Key（受限会话密钥）：
  1. 目标合约白名单：仅限与 Launchpad 相关的工厂与池子合约交互；
  2. 函数选择器限制：严格限制仅能调用 `buy()` 与 `claim()`，严禁执行 transfer 转移任何资产；
  3. 资金消费上限：设置单笔与累计消费硬顶（例如总计不得超过 500 mNVDA）；

3. **2D Nonce**

- 在一些特殊时间段可能会出现同一个标的的多种 meme 瞬间上线（比如美股财报密集披露期，可能出现 NVDA、AMD、TSLA 概念的多个 Meme 代币在同一分钟内并发上线），因此 Agent 需要同时向多个不同的代币池发送打新交易。
- 不同标的、策略和风险操作应具有独立的重放保护与顺序通道，使某个任务的 nonce 缺口不阻塞其他任务。与此同时，共享资金预算和账户级风险限制仍必须统一生效。
- 独立 nonce 不等于并行执行，不等于优先纳入，也不保证首块买入。 即使重放保护彼此独立，两笔交易仍可能争用同一池子的流动性、同一账户余额或同一消费额度。

4. **Gasless Tx**

- 散户或机构在开箱即用实例化一个全新 Agent 时，往往只为其划拨了交易本金（如 1000 NVDAx 或 USDT），却没有预先准备 Mantle 原生 MNT 代币。Agent 因缺少 Gas 无法启动，Agent 可以通过平台赞助或以报价资产结算费用完成交易，并对单笔费用、累计费用、换算价格及失败交易收费设置明确上限。Sponsor 不可用时，应允许切换其他付款路径，而不是让 Agent 永久停止工作 

### 2.2 Onchain Perps 的业务场景对账户的需求 

与 Meme Launchpad 主要围绕资产买入、卖出和流动性管理不同，Perps 的账户需要持续管理交易权限、保证金、未成交订单和已有仓位。Agent 不仅要能快速下单，还需要在市场变化、密钥失陷或基础设施故障时及时降低风险。 

<Tip>
  Perps 我们可以分成：

  - 直接链上交易模式：用户或 Agent 为下单、撤单、改单分别提交链上交易。
    - 如果不做性能优化或者对应交易的原生化处理，根据 Rise 团队测的 Solidity 撮合成本，Mantle 60M 的 gas limit 只能做 14-25 笔撮合
  - 链下撮合、链上结算模式：Agent 签署订单消息，由撮合者或 keeper 提交成交与结算。
    - 如果选择这种方式就意味着放弃了 perps 与 DeFi 的可组合性，简单来说就是放弃了 Hyperliquid 的 HLP Vault 的可能（即用户失去了赚取买卖点差和清算费的途径）
</Tip>

 简单总结一下在 onchain perps 场景下的业务需求和用户行为：

1. 支持开仓、加减仓、撤单、改单、止盈止损，以及保证金的存入和调整。
2. 支持多个策略或 Agent 在同一资本所有者授权下运行，同时具有可区分的市场权限、资金预算和风险额度。
3. 支持交易费用及执行费用的代付，避免 Agent 因缺少原生 Gas Token 无法进行风险操作。
4. 在 Agent 失陷、策略异常或连接中断时，资本所有者能够撤销权限、取消未成交订单，并保留必要的减仓与恢复能力。 

对应的用户行为就是：

1. 做市 Agent 持续更新多个市场的报价，频繁撤单、改单，并进行库存对冲。
2. 策略 Agent 根据价格、资金费率或外部信号自动建仓、调整仓位。
3. 风控 Agent 监控保证金与仓位风险，在触发阈值时补充保证金、撤销风险订单或执行减仓。
4. 普通用户、机构或金库保留资金管理权，仅向 Agent 授予限定范围的交易执行权。 

因此我们总结一下在 perps 上核心的账户需求：

1. **交易权限、资金管理权与风险控制权分离**

- 资本所有者不应为了让 Agent 交易，就把账户根密钥或提款权限交给 Agent。账户应支持给不同 Agent 配置受限权限，例如：
  - 仅允许操作指定 Perps 协议、市场或子账户；
  - 允许下单、撤单和受约束的保证金操作，但不允许任意提款、修改管理员或提升自身权限；
  - 限制单笔订单规模、累计交易额度、仓位敞口和允许的价格范围。

2. **独立任务 nonce 通道与紧急操作路径**

- 同一账户可能同时进行多市场报价、对冲和保证金管理，不应因一个普通任务的 nonce 缺口而阻塞其他任务。因此，账户需要独立的任务通道，例如按策略、市场或操作类别区分，使某笔报价交易未被纳入时，不妨碍独立的撤单或保证金操作。
- 但是，独立 nonce 只能减少顺序依赖，不能保证紧急操作优先执行。 紧急撤单、减仓和权限撤销，还需要对应的提交路径、接纳规则及费用策略；共享保证金和全局风险额度也不能因为使用不同 nonce 而被绕过。

3. **同链操作的原子批处理与明确的失败边界**

- 账户应支持将紧密关联的操作放进同一个原子批次，例如：`授权抵押资产 → 存入保证金 → 创建订单`以及`撤销旧订单 → 创建替代订单`
- 但需要区分原子创建请求与原子成交。如果订单后续依赖撮合、预言机或 keeper 执行，那么一次交易中成功创建多个订单，并不保证它们未来同时成交。

4. **Gas 代付、费用上限与保证金扣费接口**

- Agent 应能在没有原生 Gas Token 的情况下执行交易和必要的风险操作，并对单笔、累计及失败操作的费用设置上限

5. **密钥生命周期、订单取消**

- 账户应支持交易键的到期、轮换和撤销，且不应要求把资本所有者的根密钥长期放在 Agent 的在线环境中
- Perps 还需要独立的应用级紧急控制，例如批量撤销未成交订单、暂停新增风险订单，以及只允许减仓的受限操作路径。对于持续报价的 Agent，还可以考虑连接中断后自动撤单的“失联保护”机制（Hyperliquid 有）

## 3. 现存的 AA 方案综述 

### 3.1 应用层 AA 方案 

#### 3.1.1 ERC-4337 简介 

目前在应用层的 AA 方案我们只需要介绍 ERC-4337，这是使用最广泛的 AA 方案，它的思路很简单：在不修改以太坊共识层与 EVM 执行层的前提下，通过纯合约层与链下中继网络实现智能账户。 

#### 3.1.2 ERC-4337 与当前场景的不适配性 

虽然 4337 依然是目前最 mass adoption 的 AA 方案，但是我们认为它并不适合我们当前的场景，有几个最关键的点：

1. **不可预测的额外时延**

- 如果我们使用 4337，用户签署的 `UserOp` 并不会直接进行 mempool 然后被 Sequencer 打包，而是通过 Bundler 在链下随机打包多个 `UserOp` ，在 Meme Launchpad 首块抢开盘或 Perps 毫秒级清算自保时，这一延迟足以导致 Agent 的交易被传统 EOA 或直连节点穿透狙击。

2. **高额的额外 gas**

- 所有逻辑全部在 EVM 应用层模拟，每一笔 `UserOp` 执行时，`EntryPoint` 必须进行多次跨合约外部调用、复杂的上下文切换、严格的参数重打包与状态检查

3. **公共 Bundler 的 MEV 抢跑问题** 

- UserOp 在链下 Bundler mempool 中是以明文存在的。由于 Bundler 拥有决定包含顺序和是否打包的绝对裁量权，运行在公有网络的恶意 Bundler 可以轻易解析 Agent 的抢买或套利参数，实施 Front-Running 或 Sandwich

4. **2D Nonce 的需求依然存在**

- 在执行层面，Bundler 最终将这一批 `UserOps` 提交到链上时，依然是以 Bundler 自身的 EOA 身份发起一笔标准以太坊交易，换言之，整个 Bundler 节点的对外出口依然卡死在底层单调自增的 EOA Nonce 上，因此存在一个约束：同一个 Bundle 内默认不能包含同一个 EOA 的多笔 UserOp
- 但是实际上 4337 已经实现了 2d nonce，将 uint256 nonce 分成高 192 位 key 与低 64 位 sequence，由 `EntryPoint` 为每个 `(sender, key) `维护递增序列，但这个实现是需要跨 Bundle 的 

### 3.2 协议层 AA 方案 

因此这也正是为什么我们在拥有 4337 这样成熟的应用层 AA 方案后还需要讨论协议层 AA 方案的原因，4337 无法解决应用层包装带来的时延、Gas 损耗与并发死锁。而我们在协议层的 AA 方案中也只看目前比较流行且在 Mantle 上已经支持的方案。 

首先我们要确认的是我们无法像 zkSync 和 StarkNet 这样直接废除 EOA，让所有账户均为一等公民的智能账户，这样的设计固然对 ux 有好处，但是失去了 evm 等效的这个最大特点，同样也是因为这个原因，在 Ethereum L1 没有确定 Native AA 的方案前，Mantle 也无法选择 Native AA 的方案（8130 or 8141） 

#### 3.2.1 EIP-7702 

7702 的核心机制包括：引入 `0x04` 交易类型，交易 payload 中允许携带 `authorization_list`。用户通过签署授权，将其已有的 EOA 地址在当前交易的执行生命周期内，临时将其 code 指向一个预先部署的智能账户实现合约；

- 优点
  - 这个方案最大的优势在于数以百万计的存量 EOA 钱包无需部署新合约或转移资产，即可瞬间获得 Multicall、Gas Sponsor 等高级能力
  - 智能账户无需在链上持久化部署代码，免去了数十万 Gas 的合约部署费用
- 缺点
  - 尽管可以在被委托的合约内部维护逻辑 Nonce，但从 L2 节点与 Mempool 排队视角来看，该 EOA 的交易池排队依然受制于底层的标量递增 Nonce，无法彻底解决多线程并发 

#### 3.2.2 RIP-7560 （未支持，但是可以关注） 

RIP-7560 定义新的 AA 交易，将账户部署、账户验证、Paymaster 验证、业务执行与后处理纳入协议规定的阶段。简单来说，你可以把它理解为是 4337 的协议层复写，4337 所有的组件都可以在这个 RIP 当中找到对应：

- 链下 Bundler → 直接由节点的 Sequencer / Block Builder 取代；
- 链上 EntryPoint 单例合约 → 变成底层执行内核内部的伪地址 AA_ENTRY_POINT (address(7560))；
- 应用层的 UserOperation → 升级为符合 EIP-2718 标准的原生交易类型 AA_TX_TYPE；
- 合约验证接口 validateUserOp → 变成内核直接调用的 validateTransaction。 

因此其实 RIP-7560 的用户交易生命周期也和 4337 类似，这里我们就不多赘述了，大概就是：

1. 用户通过工厂合约和用户初始化参数算出一个智能账户地址 sender，然后将资产 deposit 进到这个 sender 地址即可
2. 后续的交易都可以通过 EOA 去发起，但是 `AA_TX_TYPE` 交易中的 sender 会是智能账户合约地址
3. 节点收到交易后会调用 `validateTransaction` 去发起对交易的校验，完成后最终交易完成 

当然，7560 将所有的逻辑都下放到了协议层，主要就是为了解决作为应用层方案的 4337 中存在的一些问题，比如高额的 gas，额外的链下延迟等问题都不存在了，但是也引入了一些新的问题：

1. 需要 hardfork
2. 2d nonce 没有原生支持，需要和 RIP-7712 结合实现
